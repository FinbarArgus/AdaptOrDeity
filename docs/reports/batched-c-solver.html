BE_batched_c: a CellML solver for many weakly coupled parts

A new libcuflynx solver that splits a model into independent blocks of states, integrates each block on its own with an implicit method and an exact Jacobian, all in generated C, on several threads. On the AdaptOrDeity colony it is 35–120× faster than CVODES at the same or better accuracy, and it sets up in seconds instead of minutes.

The short answers

Is libCellML used?

Yes, for parsing, flattening and analysing the model (our combined libCellML build, 0.7.1 with our speed-up and units PRs). libCellML's own generated C is used too, but only off the hot path: initial values, computed constants and the algebraic variables written to outputs.

Is the C for the rates libCellML's?

No. The rates and the Jacobian are printed by our own code from libCellML's analysed equation trees. That is the faster option: each block computes only the algebraic variables its rates need, over its own small arrays, and identical cells share one function. libCellML's computeRates would compute every algebraic variable of the whole model on every call, and it has no Jacobian.

Are the #520 templates used?

Yes. The solver renders four Jinja2 templates through #520's template_environment(), takes libCellML's C through #520's core_code(), and builds with #520's build_library() (CMake). It does not use #520's model0d templates, which are for the CVODE/RK4 C++ model.

What is slow, then?

Only the first setup. For 64 cells the first load takes about 65 s, of which about 40 s is libCellML parsing, flattening and analysing. The built library is cached under a digest of the CellML files, so later loads take about 0.1 s. CVODES through Myokit needs 821 s to build the same model, every time it changes.

From CellML to a running library

libcuflynx

Module array → one flat CellML file

The usual generation: module_array.json and parameters become the model's CellML. Nothing new here.

libCellML

Parse, flatten, analyse

The analyser orders the equations and classifies every variable (state, constant, computed constant, algebraic, external). Its equation trees are the input to everything below.

kernel_ir.py

Blocks, programs and kernels (language-neutral)

The equation trees become plain tuple expressions. States are split into blocks: the connected components of "this rate reads that state", through the algebraic variables in between. For each block a rates program holds only the algebraic variables its rates need, in dependency order. Forward-mode differentiation of the same trees gives the Jacobian program and its sparsity pattern (ported from AdaptOrDeity's jacobian.py). Blocks whose programs match once states and inputs are numbered locally share one kernel.

cpp/batched.py

Print C and render the templates

A thin emitter prints the expressions as C and renders batched_kernels.c/.h, batched_runtime.c and CMakeLists.txt. libCellML's C is added as model0d_core.c/.h (one variables array, from #572), compiled at -O1 because it only runs at setup and for outputs.

CMake

Build one shared library

Release build with OpenMP, in a folder named after a digest of the sources, so an unchanged model is never rebuilt.

batched_c_helper.py

Run it like any libcuflynx solver

Loaded with ctypes behind the same SimulationHelper surface as the Myokit helper, so ProtocolExecutor and obs_data.json protocols run unchanged. Choose it with solver: BE_batched_c; solver_info takes method (backward_euler or trbdf2), rtol, atol, MaximumStep, MaximumNumberOfSteps, threads and jacobian.

For a colony of 64 identical fermenter cells this gives 64 blocks and one kernel: one rates function and one Jacobian function, called with each cell's own states and inputs.

What the generated C looks like

Each kernel is two functions over a block's own arrays: y its states, in its inputs (constants, computed constants and anything shared), dy its rates, J its Jacobian.

/* Kernel 0: 25 states, 278 inputs, used by 64 block(s). */
static void rates_0(double t, const double *y, const double *in, double *dy)
{
    double a12 = in[3] * y[0] / (in[7] + y[0]);   /* only what the rates need */
    ...
    dy[0] = a12 - in[41] * y[0];
}

/* 248 structurally non-zero entries of 25x25. */
static void jacobian_0(double t, const double *y, const double *in, double *J)
{
    double da12_0 = (in[3] - (a12 / (in[7] + y[0]))) / (in[7] + y[0]);
    ...
    J[0] = da12_0 - in[41];
}

Illustrative, with the shapes the template produces; the real file has one pair per kernel and a table BK_KERNELS[] that the runtime indexes.

How a block is integrated

  • An L-stable implicit one-step method per block. Backward Euler (first order, cheapest step) or TR-BDF2 (second order: a trapezoidal stage, then BDF2; the method of MATLAB's ode23tb). Each block has its own step size, so quiet cells take long steps while a busy one takes short ones.
  • Modified Newton with the exact Jacobian. The Jacobian and the LU factors of I − aJ are kept across iterations and steps, and redone when Newton slows or fails, after a set number of steps, or when a changes. Entries that come out non-finite fall back to finite differences.
  • Convergence tested on Newton's update, scaled by its observed rate, as CVODES does. Testing the residual failed on the neonatal model, where a rate is a near-cancellation of terms around 10¹⁵ and the residual is all rounding.
  • Error control. The local error estimate, weighted by rtol·max|y| + atol, sets the next step. When it would reject a step it is first filtered through (I − aJ)⁻¹, as Radau5 does, so a fast mode the method already damps is not counted as error.
  • Outputs by cubic Hermite interpolation from the states and rates at both ends of a step, so steps are never cut short to land on output times.
  • Cheap restarts. Between sub-experiments a block whose inputs did not change carries on with its step; a changed block restarts from its current state with a short step.
  • Threads. Blocks are independent, so OpenMP runs them on any number of threads with bit-identical results.

Where it wins

  • Many weakly coupled parts: 1–2 orders of magnitude, linear in the number of blocks.
  • Small and medium models at errors around 10⁻⁴–10⁻⁵: 2–10× faster.
  • Heart circulations: as fast as CVODES at its defaults and more accurate (those defaults are 4–60% off on valve states).
  • No heavy build: under a second for these models, then cached.

Where it loses

  • Very tight accuracy: CVODES varies its order up to 5; these methods are first and second order.
  • Oscillators: Van der Pol is 5% off at rtol 1e-6 against CVODES' 0.5%; backward Euler's phase error makes it unusable there.
  • One large tightly coupled block (200+ states): dense LU makes it about 1.3× slower than CVODES at rtol 1e-6.

What the stress tests caught

  1. Heart models failed at t = 0: flows start at rest with rates near 10¹⁰ through tiny inertances. Fixed with the error filter and a minimum step defined by t + h = t.
  2. Newton never converged on the neonatal model (rounding-only residual). Fixed by testing the update, as CVODES does: 234k steps fell to 5.2k with TR-BDF2.
  3. Backward Euler's phase error on oscillations and heart cycles: the reason TR-BDF2 was added.
  4. Two bugs in #572's C generation (a model with no algebraic variables, and states initialised by computed constants). Both fixed, tested and now pushed to #572.
  5. A model that leaves its domain (the square root of a negative) or slides along a jump in its rates: this solver stops with a clear error, where CVODES spins without end.

Each fix has a test that fails without it. The branch's own tests: 16; with the related suites, 199 passed and 7 skipped.

Not done yet

  • Protocol traces (time series in params_to_change), external variables, algebraic loops and sensitivities.
  • Sparse LU for single blocks of more than about 100 states.
  • Splitting one-way coupled blocks further (strongly connected components).
  • A big MaximumStep can skip a sharp driven feature: heart models should set one, as libcuflynx's configs do for CVODE.
  • The build cache locks with fcntl, so it is POSIX only for now.
  • control_phys differs from CVODES by 13% on one state, and CVODES fails at tight tolerances there, so which is right is open.

What it means for AdaptOrDeity

The game's cells now run on it. Each cell is an instance of the cell model in the library (a new runtime API: create, copy for a daughter, advance one world step, change parameters), stepped from the game's own worker threads, so results stay bit-identical on any number of threads. The NativeAOT simulation library links the C in; Unity's Mono fallback loads it as a plugin.

  • Within 0.2% of the game's old integrator run at rtol 1e-6, on every state.
  • About twice the colony speed per thread: 256 cells run at 521× real time on 8 workers (was 275×); 64 cells at 1,804×.
  • In Unity, 120 simulated seconds headless: 0.010 s through the NativeAOT library, 0.027 s under Mono (were 0.028 s and 0.084 s).

Still to move: the algebraic values the game reads (it computes them with its old C# kernel from the C states), then the old kernel generator and integrator can go.
