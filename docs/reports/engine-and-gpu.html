Engine and GPU options for many cells

Should we drop Unity for our own .NET engine, how much faster would the cell simulation get, and when does a GPU actually help? Measured on the development laptop with our real cell kernel, plus what other games and simulation tools do.

Short answer

  • Most of the speed-up does not need a new engine. Generating the cell kernel in a lean layout and running cells on all cores gives about 7–8× over today, inside Unity.
  • Leaving Unity's Mono runtime adds about 2× more (measured, same code), and modern .NET's SIMD adds about 3× on top on one core. Together, roughly 20× over today's path per core.
  • A custom engine is feasible: the Unity side of the game is only ~1,600 lines (immediate-mode panels, sprites, lines, a camera). But we would own windowing, text, UI, audio, builds and every platform. A lighter option gets the runtime gain while keeping Unity: compile the simulation with .NET NativeAOT and load it into Unity as a native library, or wait for Unity 6.8's CoreCLR player.
  • The GPU pays in single precision only. Our kernel in float runs ~35× faster than the best CPU path; in double it is no faster than the CPU on a consumer GPU. Single precision is risky for stiff cell chemistry, so use the GPU first for the environment field and drawing, and treat GPU cell kinetics as a gated experiment.

Own engine

How hard is it to leave Unity?

Our simulation already lives in plain .NET libraries, and the Unity side is small: about 1,600 lines using immediate-mode panels (GUILayout, 104 uses), sprites, line renderers and a camera. A replacement front end for what exists today is weeks, not months. The cost is everything Unity does that we have not needed yet and will: text and player-facing UI, audio, input across devices, asset pipeline, builds, code signing and notarisation on macOS, and any console or web port.

Precedents both ways: Celeste, Stardew Valley and Barotrauma shipped on MonoGame; Terraria reached desktop through FNA; Thrive moved to Godot with C#; Factorio and Noita have custom engines. Oxygen Not Included is the closest to our design: a Unity front end with the simulation in a separate native library.

Explainer

How a GPU computes, and when it pays

CPU: a few clever cores

14 cores

Each core runs its own instruction stream fast, guesses branches, and hides memory delays with large caches. Each can work on four doubles at once (AVX2). Good at different work per item, branches, and small batches.

GPU: thousands of simple lanes

1 warp

Lanes run in groups of 32 (a warp) that execute the same instruction together. While one warp waits for memory, the GPU switches to another, so it needs tens of thousands of work items to stay busy. Our laptop GPU has 16 multiprocessors; a gaming card has 60–130.

What decides whether it is faster

  • Same work for every item. One cell per lane works when every cell runs the same equations. When lanes branch differently (one cell needs three Newton iterations, its neighbour ten), the warp runs both paths and the rest of the lanes wait.
  • Precision. Consumer GPUs do double-precision arithmetic at 1/32 to 1/64 of their single-precision rate; Apple's Metal and WebGPU have no doubles at all. Our measurement shows it: float 3.4 ns, double 149 ns.
  • Getting data there and back. Launching work costs microseconds, copying results back costs milliseconds (1–7 ms for all rates of 65k–262k cells), and in Unity results arrive a frame or more later. Data must live on the GPU across many steps; read back only small summaries.
  • Enough items. Below a few thousand items the fixed costs win and the CPU is faster. Obi's Unity physics documents exactly this crossover.
  • Arithmetic per byte. Simple stencils (diffusion) are limited by memory bandwidth, which GPUs have plenty of; heavy per-item maths (our cells, with exp/log) needs the arithmetic rate, which is high in float only.

What other games do: Thrive, Oxygen Not Included, Noita, From Dust and Factorio all simulate their fluids or chemistry on CPU threads in chunks and use the GPU to draw. GPU fluids appear where the fluid itself is the product (Zibra Liquids, Obi's compute backend), and in reaction-diffusion demos that keep everything in GPU textures.

Recommendation

Path forward

  1. Measure the runtime we ship. Run the kernel benchmark in a Unity IL2CPP player and the experimental CoreCLR player, next to Mono and .NET.Decides how much a runtime change is really worth.
  2. Lean kernel layout and all cores, inside Unity. kernelgen change, batched integrator, fixed chunks.~8× now, no engine decision needed. Already step 1–3 of the parallel plan.
  3. Prototype the simulation as a NativeAOT library loaded by Unity. Same libraries, compiled ahead of time with .NET 10, intrinsics enabled; Unity keeps rendering and UI.Gets the ~2× runtime and ~3× SIMD gains without rewriting the front end. Fall back to the managed build where AOT is a problem.
  4. GPU for the field and drawing; GPU cell chemistry only behind gates. Float accuracy over hours of play, ≥5× over the CPU path including transfers, a CPU fallback.Generate the GPU kernel (HLSL, or C# through ILGPU in a non-Unity build) from the same equations.
  5. Revisit leaving Unity if step 3 fails or the game needs things Unity makes hard. Godot 4 C# is the lowest-risk engine unless the web matters; an ImGui app on Silk.NET is the cheapest if the game stays panel-heavy.
