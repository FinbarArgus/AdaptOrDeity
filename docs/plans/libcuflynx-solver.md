# Cells on libcuflynx's generated C and solver

Decision (2026-10-12): the game's cells move from AdaptOrDeity's own C# kernels (`tools/kernelgen`) and integrator
(`BackwardEulerIntegrator`, `FermenterCell`'s adaptive stepping) to libcuflynx's `BE_batched_c`: kernels generated as
C from libCellML's analysis (`generators/kernel_ir.py`, `generators/cpp/batched.py`) and its runtime (adaptive backward
Euler or TR-BDF2, modified Newton with the exact Jacobian). Report: [docs/reports/batched-c-solver.html](../reports/batched-c-solver.html).

Why: on the colony protocol of `tools/interop` it is ~19x faster than the game's C# on one thread at rtol 1e-4 and
more accurate (0.20% from CVODES with TR-BDF2 against 1.19%), its rates take 258 ns per cell against 400-650 ns, and
its Jacobian 0.74 us against 3.9 us. One generator then serves libcuflynx, PhLynx and the game (issue #573).

## What the game needs that the runtime does not have yet

The runtime integrates the blocks of a fixed module array, all at once, on OpenMP threads (`bk_run`). The game:

- adds and removes cells as the colony grows and dies;
- advances each cell by one world step (0.1 s) from its own worker threads (`ParallelWork`), so results stay
  bit-identical for any number of workers and food and forces can be settled between steps;
- changes a cell's parameters at any time (player traits and controls, food at the membrane, the motor) and reads a
  few algebraic variables after every step (uptake, thrust, growth progress, pH; `outputs` in modules.lock.json),
  the rest only for the inspected cell.

## Done (2026-10-12)

- **libcuflynx instance API** (feat/batched-implicit-solver, 22e08b59): `bk_instance_create/copy/destroy`,
  `_advance`, `_parameters_changed`, `_restart`, `_compute_variables`, `bk_state_info/bk_variable_info`; the library
  carries its block table. Tests: analytic solutions, a changed parameter keeps the states, eight threads bit-identical
  to one, a copy continues bit for bit.
- **The cell library**: `tools/scripts/build_cell_library.py` (libcuflynx venv) builds `libaod_cell.so` and
  `libaod_cell.a` from content/assembled in ~3 s.
- **Game cells on it**: `NativeCell` (Sim.Physiology) maps the C# kernel's states and externals by name;
  `FermenterCell.NativeIntegration` (default true) hands it the integration when the library loads, else the C#
  integrator runs. Algebraic values still come from the C# kernel. Within 0.2% of the C# cell run at rtol 1e-6;
  native colonies bit-identical on any number of workers; ~2x the C# colony per thread (256 cells: 521x real time on
  8 workers).
- **Packaging**: the NativeAOT library links `libaod_cell.a` in (DirectPInvoke); Unity's Mono loads `libaod_cell.so`
  from the plugin folder. In Unity both run native cells with byte-identical frames (120 s headless: NativeAOT 0.010
  s, Mono 0.027 s, from 0.028 and 0.084).

- **Algebraic values from the library** (2026-10-12): `kernel_ir.outputs_program` and `bk_instance_outputs` compute
  the lock's 17 outputs after each step; `bk_instance_compute_variables` the rest on demand. Every value matches the
  C# kernel's on the same state. The C# kernel only gives a new cell its initial values.
- **Every desktop platform**: the generated C is committed (`src/AdaptOrDeity.Cells/generated`, regenerated by
  `build_cell_library.py`) with a CMake build of `aod_cell` and `aod_cell_static`; `.github/workflows/native.yml`
  builds both, the NativeAOT library with the cells linked in, and checks them on Linux, Windows and macOS
  (`AOD_REQUIRE_NATIVE=1` makes a missing library a failure, not a skip).
